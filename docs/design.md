# ot-demo-3d 設計メモ — Windows + JRU だけで作る「攻撃→溢水→復旧」体験

最終更新: 2026-11-10 / 対象: OTセキュリティ研究会 第1回WS（の代替案）

## 結論（先に）

物理ポンプ・タンク・PLC実機が手に入らなかった。これらを**ws01のソフトシミュレータ＋3D可視化**で代替し、
**EWS侵害とJRU復旧だけは実機Windowsで本物**にする。こうすると「CG＝台本アニメ」問題が消える:

- 3Dは**本物のModbusレジスタ値を映すだけの計器**。参加者が本当に書き換えれば、本当に水位が動く。
- 乗っ取りも復旧も**実機Windows上で本物**に起きる（擬似ランサム→JRUが実ディスクを書き戻す）。

当日は**ハンズオン**（参加者が自分の手で侵害）を最優先。各段で「なぜ効くのか（仕組み）」が
目に見えることを必須要件にする。JRU復旧の山場は**差分方式（blocks, 目標5分）でライブ**。

## 全体構成

```
 参加者ごと（各自のPC/VMでスケール, 安全・無害）         共有の実機（山場, 1セット）
 ┌─────────────────────────────┐          ┌──────────────────────────┐
 │ [攻撃端末]                  │          │ [Windows EWS 実機(VAIO)]   │
 │  nmap / Wireshark / python  │          │  制御プロジェクト(フォルダ) │
 │      │ 認証なしModbus/TCP   │          │      ▲ 擬似ランサムで暗号化  │
 │      ▼                      │          │      │ ディスクに永続       │
 │ [PLC = ws01シミュレータ]     │          │ [JRU装置(Raspberry Pi 5)]  │
 │      │ レジスタ/コイル生値   │          │  基準状態→点検→承認→書戻し │
 │      ▼ (WSブリッジ)         │          └──────────────────────────┘
 │ [3D溢水画面 = 生計器]        │
 └─────────────────────────────┘
```

**役割分担の理由**: 偵察〜溢水は無害・無限にスケールするので**全員が自分の手で**体験。
EWS侵害＋JRU復旧は実機1セットなので**共有の山場**として全員で見る（各ステップを参加者が操作）。

「仕組みが見える」ための仕掛け:

- **②→考察でPLCを一度再起動**させ「揮発 vs 永続」を体で理解させてから③へ進む（③の必然性が立つ）。
- **④の点検画面で差分（変わったブロック/ファイル）を一覧表示**。復旧が魔法ではなく「差分を基準へ戻す操作」だと見せる。

## Windows攻撃シナリオ（段階式・隔離ラボ・全て実物に対して）

前提: 学内/会場網から**物理・論理的に隔離**した閉じたセグメント。攻撃スクリプトはこの中だけ。

### ① 偵察（無害・全員）
- `nmap -p- <PLCのIP>` でModbus/TCP(5020)を発見。
- Wiresharkで read/write パケットを観察 → **認証ハンドシェイクが無い**ことを確認。
- 仕組み: Modbus/TCPは設計上認証を持たない。到達できれば誰でも読み書きできる。

### ② プロセス改ざん（無害・全員・自分の3Dが溢水）
- ws01の `attacker/attack.py` 相当を自分で叩く:
  - コイル `CO_SAFETY=False`（安全インターロック無効化）
  - 保持レジスタ `HR_SETPOINT_HI=0xFFFF`（停止水位を到達不能に改ざん）
- 結果: 制御ロジックが「上限まで給水し続ける」状態 → **溢水ラッチ**。3Dの水が床へあふれる。
- 仕組み: 安全は「PLCロジック＋設定値」に依存。両方を外部から書けるなら物理が危険側へ振れる。

### 考察（揮発 vs 永続の分岐）
- PLCを再起動 → レジスタは初期化され**正常化してしまう**。
- 「では永続的に壊すには？」→ 制御プロジェクトを持つ**EWSのディスク**を狙う、へ接続。

### ③ EWS侵害（実機Windows・共有・擬似ランサム）
- `~/workspace/otlas/JRU/poc/demo/ransom-demo.ps1` を使用（**無害・可逆XOR**、目印 `JRU-DEMO-OK.txt`
  のあるデモ専用フォルダのみ対象。Windows/Program Files/ドライブ直下は拒否）。
- 結果: 制御プロジェクト相当のファイルが `.locked` 化＋脅迫文。**電源断でも消えない**。
- 仕組み: 被害がディスクに残る＝バックアップから戻す以外に復旧手段が無い。ここがJRUの出番。

### ④ JRU復旧（実機・共有・差分方式でライブ）
- JRU装置(Pi5)から点検OS(USB)起動 → 点検（NTFS/GPT差分, Windows正常変化は除外）→ Web画面で**人が承認**
  → **差分だけ書き戻し(blocks)** → 再点検で変化0件 → Windows再起動 → ファイル復活・sha256一致。
- 仕組み: 基準状態（全ディスクイメージ）と現状の**違うチャンクだけ**をUSB経由で書き戻す。

> 注: ①②は各自のPC/VMで無害にスケール。③④は実機1セットの共有ステップ。
> ③の擬似ランサムは「対象フォルダ限定・可逆・システム領域拒否」で安全。本物のマルウェアは使わない。

## 3Dの「生計器化」（WSブリッジ）

現状の3D（`demo/index.html`）は内部シミュレーション。これを**本物のModbus値駆動**に変える:

- ブラウザは生のModbus/TCPを話せない → **小さなローカル常駐プロセス**を1つ足す:
  `[ws01のModbusサーバ] ←Modbusポーリング← [WSブリッジ] →WebSocket→ [ブラウザ3D]`
- ブリッジはPython1ファイル想定（ws01の `common/modbus.py` のクライアントを流用し、
  レジスタ0=水位, 1=停止SP, コイル0=ポンプ, 1=安全IL, 2=溢水 を定期読み出し→JSONでWS配信）。
- 3D側は内部physicsを止め、**受信値をそのまま描画**。攻撃スクリプトが書けば即座に反映。
- ローカル完結（localhost）。外部送信なし。CSP的にもローカルWSのみで閉じる。

## JRU山場のライブ化と「明日の検証」

### 目標
差分方式(blocks, `~/workspace/otlas/JRU/poc/inspect-os/files/jru_blocks.py`)で、実機の書き戻しを
要件R3の**目標5分**付近に収め、**ライブで**見せられる状態にする。現状 blocks は実装済み・**実機未検証**。

### 明日の昼に検証を回すための段取り（現実解）
ボトルネックは「基準状態の取得(blocks形, 約1時間)」と「書き戻し＋点検の実測」。本気で回すなら:

1. **午前（または前夜）に先に済ませる（撮影・観客なしでよい）**
   - 新しい点検OSをビルド（`poc/inspect-os/build.sh` → `work/jru-inspect.img`）してPi5へ。
   - Windowsの高速スタートアップを切ってシャットダウン → JRUで**blocks形の基準状態を取得**（約1時間）。
     ※既存 `baseline-20261106140206` はpartclone形で互換が無いため**取り直し必須**（handoff参照）。
2. **昼イチで低コストの予行**: まずVM(段階1 QEMU)で blocks の書き戻しを一周回し、ロジックのバグを潰す。
3. **午後に実機で本番検証（実測15〜40分）**: 擬似ランサム → 点検 → 承認 → **blocks書き戻し** → 再点検0件
   → Windows起動 → sha256一致。操作画面ログの「照合/書き込み/所要」を記録しR3と突き合わせ。

### 判定
- **基準状態を午前に取れるなら、午後の検証は十分回せる見込み**（実測作業は実質15〜40分）。
- 取れない場合、午後に基準取得(約1時間)＋検証が重なり**タイトすぎる**。基準の前倒しが成否を分ける。
- 先に確認すべき実機要因（handoff/hardware-troubleshooting.md）: 内蔵SSD読み出し速度（点検時間を決める）、
  Pi5のUSB速度、BitLockerの有無（`manage-bde -status`）、休止状態ディスクの書き戻し挙動。

### フォールバック
- blocksがライブで5分に収まらない場合: 既存の撮影計画(`JRU/docs/demo-recording-plan.md`)で
  **承認まではライブ、書き戻しは早送り映像**に差し替え、最後の復活確認をライブに戻す。
